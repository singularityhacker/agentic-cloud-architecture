# ADR 003 — Independent framework, model and deployment choices

**Status:** Accepted; local implementations available, AWS adapters planned.

The custom Python loop is useful as a transparent baseline, but must not define
which framework every agent uses. Add `framework: custom-python | strands` at the
manifest root (omission preserves `custom-python`). Model bindings and deployment
targets remain independent. `AGENT_FRAMEWORK` overrides the framework at runtime.

Strands owns orchestration and tool execution. A small custom Strands Model
adapter translates the existing chat-provider contract, preserving model IDs,
prompts and tool schemas across framework comparisons. This supports rules,
Ollama and the existing optional Hugging Face adapter without implicit Bedrock
fallback. It is intentionally text/tool-chat only, not a general multimodal or
structured-output adapter. Native Strands providers and managed Harness are
future integrations, not claimed as implemented here.

Both loops use the existing policy, retrieval and SQLite memory. Each Strands
invocation gets a fresh SDK Agent and budget adapter; only explicitly keyed
memory persists across requests. The adapter bounds model calls and reserves
all requested tool calls before execution, including invalid/unknown tools.
Strands tools execute sequentially. SDK retries and context management are
disabled so they cannot introduce unaccounted model calls. Dependencies remain
optional and the tested Strands release is pinned; transitive dependencies are
resolved by pip, not claimed as a full lockfile.

Tests run the actual SDK against deterministic and mocked chat providers with
network access forbidden. This establishes adapter compatibility, not real-model
quality, AgentCore parity, performance superiority, or cloud deployment readiness.
